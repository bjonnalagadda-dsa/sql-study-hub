25. 30 Performance Tips

Database: SalesDBScript: 26_Performance_Optimization.sql

A checklist of habits that make queries faster. Always confirm with the execution plan.

Remember this

  • Don't hide indexed columns inside functions.
  • Reduce data early: filter and aggregate before joining.
  • Always test with the execution plan.

Fetching

#1Select only the columns you need, not SELECT *.
#2Skip DISTINCT and ORDER BY unless truly required.
#3Use TOP when exploring so you do not pull every row.

Filtering

#4Create non-clustered indexes on columns often used in WHERE.
#5Do not wrap filtered columns in functions: use OrderDate BETWEEN ... instead of YEAR(OrderDate)=2025, LIKE 'A%' instead of SUBSTRING.
#6Avoid a leading wildcard ('%Gold%'), it blocks the index.
#7Use IN instead of many ORs.

Joins

#8INNER is fastest, then LEFT/RIGHT, FULL is slowest. Use the cheapest that is correct.
#9Use explicit ANSI joins, not comma joins.
#10Index the columns in ON.
#11On big tables filter before joining (subquery).
#12On big tables aggregate before joining.
#13Replace OR in join conditions with UNION.
#14Check for nested loops in the plan, and use hints such as OPTION (HASH JOIN) when a big and small table are joined.

UNION

#15Use UNION ALL when duplicates are fine.
#16When duplicates are not fine, UNION ALL then DISTINCT can beat UNION.

Aggregation

#17Columnstore index for heavy aggregations on large tables.
#18Pre-aggregate into a summary table for reporting.

Subqueries and CTEs

#19JOIN or EXISTS beat IN with large lists; EXISTS is best for large tables.
#20Remove redundant logic: one CASE with a window average instead of two UNIONed queries.

DDL

#21Pick precise types; avoid VARCHAR where INT or DATE fits.
#22Avoid MAX or oversized lengths.
#23Use NOT NULL where possible.
#24Give every table a clustered primary key.
#25Index foreign keys that are queried often.

Indexing

#26Avoid over-indexing, it slows writes.
#27Drop unused indexes.
#28Update statistics regularly.
#29Reorganize or rebuild fragmented indexes.
#30For huge fact tables, partition then add a columnstore index.

Examples: bad vs good

Functions on columns stop the engine using an index. Rewrite the condition so the bare column is compared.

-- Bad
SELECT * FROM Sales.Orders WHERE YEAR(OrderDate) = 2025
-- Good
SELECT * FROM Sales.Orders WHERE OrderDate BETWEEN '2025-01-01' AND '2025-12-31'

-- Bad: correlated subquery per row
SELECT c.CustomerID, (SELECT COUNT(o.OrderID) FROM Sales.Orders o WHERE o.CustomerID = c.CustomerID)
FROM Sales.Customers c
-- Good: pre-aggregate and join
SELECT c.CustomerID, o.OrderCount
FROM Sales.Customers c
INNER JOIN (SELECT CustomerID, COUNT(OrderID) AS OrderCount FROM Sales.Orders GROUP BY CustomerID) o
ON c.CustomerID = o.CustomerID

Good table design

Compare a sloppy table (VARCHAR(MAX), no key, everything nullable) with a tight one.

CREATE TABLE CustomersInfo (
    CustomerID INT PRIMARY KEY CLUSTERED,
    FirstName VARCHAR(50) NOT NULL,
    LastName  VARCHAR(50) NOT NULL,
    Country   VARCHAR(50) NOT NULL,
    Score     INT,
    BirthDate DATE,
    EmployeeID INT,
    CONSTRAINT FK_CustomersInfo_EmployeeID FOREIGN KEY (EmployeeID)
        REFERENCES Sales.Employees(EmployeeID)
);
CREATE NONCLUSTERED INDEX IX_CustomersInfo_EmployeeID ON CustomersInfo(EmployeeID);

Common mistakes

  • Optimizing by guess, without reading the plan.

Check yourself

Why is WHERE YEAR(OrderDate)=2025 slow?

The function on the column prevents index use. Use a date range instead.

UNION vs UNION ALL for speed?

UNION ALL is faster because it skips duplicate removal.

Which join is generally fastest?

INNER JOIN.
